## 1. 背景与问题

4U 通过“人、活动、话题”帮助用户发现关系机会。个人推荐、红心、即时讨论、活动确认和聊天均依赖真实、完整且经过授权的用户资料。如果第一次建档只追求多收字段，容易造成高流失、隐私误解和低质量资料；如果字段、权限与审核状态没有明确边界，又会产生未成年人准入、隐藏信息泄漏、AI 越权和跨端状态冲突。

因此，需要一套短、透明、可恢复的首次建档流程，在 3～5 分钟内完成推荐所需的最小信息，同时让用户理解：

1. 为什么收集该信息；
2. 信息用于候选筛选、推荐排序、公开展示还是 AI 解释；
3. 哪些项目必须提供，哪些项目可以关闭或稍后补充；
4. 提交后还需经过资料审核及真人验证，不能直接进入推荐池。

## 2. 产品目标与非目标

### 2.1 产品目标

1. 让符合年龄要求的新用户完成一份可审核、可推荐的个人资料草稿。
2. 通过一屏一主题、自动保存和跨端续填，将有效填写时间控制在 3～5 分钟。
3. 在收集时完成字段级用途授权，避免把“提供字段”等同于“同意公开或用于 AI”。
4. 将账号验证、成年校验、真人验证、资料审核和安全状态独立建模并清楚反馈。
5. 在弱网、退出、刷新、切换设备及版本冲突后安全恢复，不重复提交、不丢失已同步内容。
6. 为后续推荐、个人卡、AI 解释、审核和数据分析提供版本化、可审计的数据。

### 2.2 非目标

- 不在本流程中做完整 MBTI 测试。
- 不采集实名、身份证号、精确实时位置、通讯录或第三方社交账号。真人验证所需材料由独立验证服务按最小必要原则处理。
- 不承诺资料提交后立即进入推荐池。
- 不让 AI 代替用户填写事实、判断人格、评价颜值或预测关系成功率。
- 不在 P0 提供高度动态的问卷编排、复杂成长任务或奖励体系。
- 不把通用模型训练授权作为使用 4U 或完成建档的前提。

## 3. 核心口径与本专项决策

### 3.1 “首次进入”分三种情况

| 用户状态 | 首次进入后的处理 |
|---|---|
| 未登录访客 | 可先浏览部分公开活动和话题；不立即强迫填写资料。点击个人详情或任何受限动作时，引导登录并开始建档。 |
| 已完成账号验证、档案为 `DRAFT` | 进入上次未完成的建档步骤；允许“稍后完成”，退出到仅含公开活动/话题的有限浏览模式。 |
| 已提交或已有档案 | `REVIEWING` 进入审核状态页，`REJECTED` 进入补改页，`RECOMMENDABLE` 进入原目标页或首页；暂停、封禁、注销分别进入对应状态页。 |

首次打开网站不等于同意收集资料。只有用户主动开始建档并完成账号验证后，才创建服务端建档草稿。

### 3.2 AI 授权口径

用户必须对 AI 用途作出明确选择，但“不启用”也是有效选择，不影响完成基础建档：

- AI 辅助表达：按次触发，只改写用户已提供内容，采纳前不公开。
- AI 契合与推荐：独立开关，对应 `consent.aiCompatibility`。
- 对外 AI 推荐理由：独立开关，对应 `consent.publicExplanation`；仅使用用户逐字段允许进入解释的内容。
- 通用模型训练：独立授权、默认关闭，不属于完整建档门槛。

若关闭 AI，跳过 AI 理解确认，系统仅使用必要硬条件和非 AI 的结构化规则；不能以此阻断资料审核或基础功能。上游 PRD 中“完成 AI 授权”在本需求中解释为“完成授权选择与留痕”，不解释为“必须同意”。

### 3.3 真人验证口径

真人验证与照片审核、资料审核相互独立。P0 建议把真人验证作为进入个人推荐池、发起活动和确认参加活动的必要条件，但不新增第 12 个建档步骤：

- 第 8 步照片页提供“立即真人验证”入口；用户可稍后处理。
- 用户可以先提交完整资料进入审核。
- 资料已通过但真人验证未完成时，状态页持续展示待办；用户仍不能进入个人推荐、红心、即时讨论、活动确认或聊天。

### 3.4 未完成建档的能力边界

P0 采用保守统一口径：已登录但未达到推荐准入门槛的用户只可浏览公开活动、公开话题及帮助/安全内容，可继续编辑和提交资料；不可查看个人详情、投票、收藏/申请/确认活动、发起活动、红心、即时匹配、聊天或进入任何房间。后续如需放开某项能力，应单独评审，而不是由客户端自行推导。

### 3.5 参考交互字段口径

本次参考图对三个字段形成以下确定口径，并优先于本文 v1.0 中与之冲突的数量要求：

| 字段 | 选择规则 | 是否可空 | 公开规则 |
|---|---|---|---|
| 交往意向 | 六张大卡片单选，未选择时“保存”禁用 | 否，需选 1 项 | 作为关系意图展示；可在“我的”中随时修改 |
| 兴趣 | 可滚动标签云多选，最多 5 项，按钮显示“保存（n/5）” | 是，0 项也可保存 | 用户保存时即确认将所选兴趣用于个人资料展示；推荐/AI 用途仍需独立授权 |
| 性取向 | 带定义说明的大卡片多选，不设默认值 | 是 | “在个人资料里显示我的性取向”为独立复选框，默认不勾选 |

性取向是敏感字段，不得根据自我性别、希望认识的人群或交往意向推断；也不得反向推导“希望认识的人群”。兴趣为空时允许完成建档，系统只能降级推荐解释，不得虚构兴趣。

## 4. 用户故事

1. 作为首次访问者，我希望先了解 4U 再决定是否注册，不因打开网站就被迫交出个人信息。
2. 作为新注册用户，我希望知道每一步为什么要问、谁能看到，以便放心填写。
3. 作为填写中的用户，我希望随时退出并在任意设备继续，而不是从头开始。
4. 作为不想使用 AI 的用户，我希望仍能完成建档和使用基础能力。
5. 作为资料被驳回的用户，我希望看到具体原因，只修改有问题的部分并重新提交。
6. 作为隐私敏感用户，我希望分别控制字段用于筛选、排序、公开和 AI 理由，而不是一个总开关。
7. 作为未达到服务年龄的用户，我需要被清晰、克制地拦截，且不会继续进入社交功能。
8. 作为用户，我希望通过直观卡片选择交往意向、通过标签快速选择最多 5 个兴趣，并能选择性取向但默认不向他人公开。

## 5. 页面入口、路由与准入守卫

### 5.1 建议路由

| 路由 | 页面 |
|---|---|
| `/onboarding/welcome` | 欢迎与机制说明 |
| `/onboarding/account` | 手机或邮箱验证 |
| `/onboarding/adult-check` | 出生日期及成年校验 |
| `/onboarding/identity` | 基本身份与性取向 |
| `/onboarding/preferences` | 交往意向与候选偏好 |
| `/onboarding/mbti` | MBTI |
| `/onboarding/interests` | 兴趣与生活方式 |
| `/onboarding/photos` | 照片、封面及真人验证入口 |
| `/onboarding/expression` | Prompt 与 AI 辅助表达 |
| `/onboarding/ai-review` | AI 理解确认或停用 |
| `/onboarding/privacy-preview` | 字段权限与个人卡预览 |
| `/onboarding/status` | 审核与真人验证状态 |
| `/onboarding/revise` | 驳回补改 |

步骤使用稳定语义 slug，不在 URL 中携带生日、手机号、邮箱等敏感信息。`return_to` 只接受站内白名单路由，防止开放重定向。

### 5.2 路由守卫

1. 未登录访问敏感页：跳转登录，成功后回到原目标；若是新账号，先进入建档。
2. `DRAFT` 访问受限页：跳到上次未完成步骤，并说明完成后可使用的能力。
3. `REVIEWING`：跳到状态页，不重复创建草稿。
4. `REJECTED`：跳到补改页，保留已通过字段。
5. `RECOMMENDABLE`：允许进入完整站点；再次访问 onboarding 时跳到“我的 > 个人资料”。
6. `PAUSED / BANNED / DELETED`：分别按现有账户状态处理，不回退到首页绕过限制。

准入结果必须由服务端下发，客户端不得仅根据本地 `profileComplete` 或页面完成度放行。

## 6. 全局页面结构与交互

### 6.1 页面框架

每一步均使用沉浸式表单页，不展示主站四项导航，避免误入受限能力；页面提供明确的“稍后完成，先浏览公开内容”出口。

- 顶部：4U 标识、返回、步骤进度（如“3 / 11”）、保存状态。
- 主区：标题、简短说明、“为什么需要 / 谁能看到”、当前步骤表单。
- 底部：上一步、继续；可选项同时提供“暂不确定”或“跳过”。
- PC：单列主表单，宽度不超过 620px；可在侧边展示价值说明，但不得让信息重复干扰填写。
- Mobile Web：单列全屏，支持 320～430px、`100dvh` 和安全区，主操作不被软键盘或底部 Home Indicator 遮挡。

### 6.2 全局交互规则

1. 一屏一个主题；进入页面时焦点落在标题，校验失败后聚焦首个错误字段。
2. “继续”只校验当前步骤；返回不清空数据。最终提交前执行全量服务端校验。
3. 必填项标“必填”，可选项标“选填”，不得用默认值伪造用户选择。
4. 每个敏感字段旁提供用途说明；完整生日、候选偏好、联系方式默认不公开。
5. 不以颜色作为唯一状态提示；错误同时包含图标、文案及修复方式。
6. 浏览器前进、后退、刷新均保持当前步骤；直接访问未解锁的后续步骤时回到首个未完成步骤。
7. 同一请求携带幂等键；重复点击“继续”或“提交”不得创建重复草稿或重复审核单。

### 6.3 自动保存与恢复

- 完成账号验证后创建唯一服务端草稿；每次字段失焦、选择完成或点击继续时保存。文本输入采用建议 800ms 防抖，最终以失焦/继续强制保存。
- 页面明确显示“保存中 / 已保存 / 离线未同步 / 保存失败”。只有收到服务端成功响应才显示“已保存”。
- 联系方式、完整生日、照片和自由文本不得写入 `localStorage`。离线时只在内存中暂存当前编辑，恢复网络后由用户确认同步。
- 草稿包含 `version`。保存使用版本校验；服务端返回 409 时停止覆盖，提示“另一设备有更新”，刷新服务端最新草稿后由用户确认继续。P0 不做静默字段合并。
- 再次登录默认打开服务端记录的首个未完成步骤，并展示“已恢复上次进度”。
- 对可空字段，`null` 表示“尚未确认”，空数组 `[]` 表示“用户已明确保存为空”。步骤完成以服务端 `completed_steps` 或 `confirmed_at` 判断，不能以数组是否非空判断；因此兴趣 `[]` 和性取向 `[]` 都不会导致恢复流程反复跳回该弹层。
- 草稿保留周期、过期提醒与删除 SLA 由法务和数据治理在发布前确认。

### 6.4 卡片与标签选择弹层

交往意向、兴趣和性取向复用统一的响应式选择弹层，但按字段采用不同选择规则：

- Mobile Web：接近全屏的底部弹层，顶部圆角，背景遮罩；PC Web：居中的大尺寸对话框。
- 顶部依次为标题、辅助说明和右上角关闭按钮；中部独立滚动；底部为带安全区的吸底“保存”按钮。滚动内容必须留足底部间距，不能被渐变或按钮遮住。
- 点击右上角关闭或遮罩时，不提交本次未保存修改；若与已保存值不同，提示“放弃本次修改？”；浏览器返回键行为一致。
- 单选/多选卡必须同时使用边框、勾选图标和 `aria-checked` 表达状态，不能只依赖颜色。标签使用 `aria-pressed`。
- 参考视觉状态：未选卡为浅灰底与中性描边；选中卡使用品牌强调色描边并在右侧显示勾选；主按钮可用态为黑底白字，禁用态为浅灰底灰字。具体色值复用 4U Design Token，需满足 WCAG 对比度，不在业务代码中写死。
- “保存”期间禁用重复点击并显示处理中；成功后关闭弹层并更新所属步骤，失败时保持选择并允许重试。
- 对话框打开后焦点进入标题或首个选项，焦点不得逃出弹层；关闭后回到触发按钮。

## 7. 11 屏详细需求

### 7.1 第 1 屏：欢迎与机制说明

**目标：**解释 4U 的三条关系路径、资料用途、预计耗时和隐私原则，让用户主动开始。

**页面内容：**

- 价值说明：“通过真实资料、共同兴趣和明确意愿，认识值得了解的人。”
- 流程说明：“约 3～5 分钟，可随时退出并继续。”
- 三项承诺：不会公开完整生日；不会展示单向心动；AI 不替用户表达关系意愿。
- 社区规则摘要与完整链接。
- 必须分别确认服务条款/隐私政策、社区规则，记录版本与确认时间；不得把通用模型训练授权捆绑其中。

**操作：**“开始建档”“先逛逛”。后者进入只含公开活动和话题的有限浏览模式。

### 7.2 第 2 屏：手机或邮箱账号验证

**目标：**建立可恢复、可跨端同步的账号。

**字段与规则：**

| 字段 | 规则 |
|---|---|
| 验证方式 | 手机号 / 邮箱二选一，至少完成一种 |
| 手机号 | 国家/地区码 + 号码；展示时脱敏 |
| 邮箱 | 标准邮箱格式；展示时脱敏 |
| 验证码 | 有效期、重发间隔、尝试次数均由服务端配置并限流 |

若号码或邮箱已存在，提示用户登录原账号，不创建重复账号。验证码错误、过期、发送频繁及网络异常均保留已填标识，并给出可恢复操作。验证码本身不落盘、不进入分析日志。

### 7.3 第 3 屏：出生日期与成年校验

**目标：**完成法定成年校验，并生成年龄、星座等派生信息。

**字段：**服务地区、完整出生日期。服务地区优先按用户显式选择，浏览器语言或 IP 仅可作为建议，不得自动决定。

**规则：**

- 成年阈值按服务地区和服务端日期计算，不在前端硬编码；边界日期使用该地区时区。
- 展示派生年龄和星座，允许用户检查输入；星座只是趣味弱信号。
- 完整生日仅用于成年判断和年龄派生，永不公开，不进入 AI 理由、通知正文或分析日志。
- 未达到年龄要求时立即停止流程，进入未成年拦截页；不得继续收集身份、偏好、照片或 Prompt。页面提供退出、帮助和按合规要求处理账户/数据的入口，不提供绕过路径。
- 成年校验服务异常时不得默认放行。

### 7.4 第 4 屏：基本身份与性取向

| 字段 | 必填 | 建议规则 | 默认用途 |
|---|---:|---|---|
| 昵称 | 是 | 2～20 字；过滤联系方式、商业导流和违规内容 | 个人卡公开 |
| 当前城市 | 是 | 城市级选择，不采集精确定位 | 候选地域判断；是否进入 AI 理由另行授权 |
| 自我性别 | 是 | 枚举由业务、安全与法务共同配置；允许自定义描述 | 候选资格，默认不作为 AI 理由 |
| 职业 | 否 | 0～30 字，需内容审核 | 用户选择是否公开 |
| 性取向 | 否 | 带定义说明的卡片多选；不预选、不限制为单选 | 敏感字段，默认仅自己可见 |

性别枚举、展示文案和“自定义”审核规则须在开发冻结前确认。用户可以不公开自我性别，但要进入个人推荐池，仍需授权其用于双向候选资格判断。

#### 性取向选择弹层

标题为“你的性向是什么？”，辅助文案为“请选择所有适用选项，描述你的身份认同”。首版参考选项如下，最终术语和释义须经本地化、法务及多元包容性评审后冻结：

**完整门槛：**2～6 张照片，推荐 4 张；至少 1 张通过“清晰单人照”检测；必须指定 1 张封面。

| 刷新/浏览器返回 | 恢复服务端已保存步骤；未保存编辑按页面状态提示 |
| 重复提交 | 同一幂等键只生成一个资料版本和一个有效审核任务 |

审核 SLA、复核次数、草稿保留周期及受限地区策略需在上线前确定。

## 11. 数据对象与接口约束

### 11.1 建议新增 `OnboardingDraft`

现有公开 `Person` 类型要求照片、兴趣等非空，不适合承载分步未完成数据。应新增独立草稿对象，完成审核后再投影为公开 `Person`：

```text
OnboardingDraft
  draft_id, user_id, onboarding_version, version
  current_step, completed_steps, profile_status
  account_verification_status, adult_status
  identity, sexual_orientations: null | string[]
  show_sexual_orientation: boolean, sexual_orientation_taxonomy_version
  relationship_intent, candidate_preferences, mbti
  interest_ids: null | string[0..5], interest_taxonomy_version, lifestyle_answers
  staged_media_ids, cover_media_id, prompt_answers, optional_bio
  ai_consent, ai_summary_version
  field_usage_permissions, policy_acceptances
  confirmed_at_by_field, created_at, updated_at, submitted_at
```

服务端保存允许字段缺失的草稿；只有满足完整门槛且审核通过后，才生成符合公开 DTO 的投影。不得为了满足现有 `Person` 必填类型而伪造职业、自我介绍、MBTI 或其他用户未提供的事实。

### 11.2 与现有合同的兼容要求

- 档案状态沿用 `ProfileStatus`，不新增 `profileComplete` 布尔值。
- 交往意向扩展为 `LONG_TERM_PARTNER / LONG_TERM_OPEN_TO_SHORT / SHORT_TERM_OPEN_TO_LONG / SHORT_TERM_FUN / NEW_FRIENDS / FIGURING_OUT`。现有 `RelationshipGoal` 三值枚举不足，需做显式数据迁移；禁止按文案相似度静默折叠。
- 性取向采用稳定 ID 数组与独立 `showSexualOrientation: boolean`；参考词库 P0 最多 10 项，服务端按词库版本校验合法性、去重和数量。公开投影只在开关为 `true` 且数组非空时包含该字段。新老用户迁移后的公开值一律默认为 `false`，不得根据旧资料或已选值自动开启。
- 兴趣保存稳定 ID 数组，数量为 0～5，并携带词库版本；不保存展示文案作为唯一事实来源。
- MBTI 支持 16 型与 `UNSURE`；星座由生日派生。
- 照片最终投影包含稳定 ID、URL、宽高和中性替代文本。
- 授权至少能投影到 `aiCompatibility`、`publicExplanation`、版本及更新时间。
- 场景隐私至少兼容 `showAge`、`showZodiac`、`showSexualOrientation`、`showInConfirmedParticipantLists`、`CONFIRMED_ACTIVITY_ONLY` 和锁屏预览隐藏。
- 公开个人 DTO 必须排除联系方式、完整生日、候选偏好、内部排序分、未授权字段和验证原始材料。现有 `Person.interests` 的非空数组约束必须调整为允许空数组或省略字段；卡片和详情在无兴趣时隐藏兴趣模块。
- 所有写请求携带 `draft_id + version + idempotency_key`；权限和资料分别有版本号。

## 12. 隐私、安全与审核要求

1. 遵循最小必要收集；展示、筛选、排序、解释分别授权。
2. 完整生日、联系方式、候选偏好、性取向、验证材料不出现在普通分析日志；性取向仅在用户独立开启公开后进入公开接口，且仍不得进入 AI 理由、通知或搜索索引。
3. 通用模型训练默认关闭；拒绝不得降低基础服务质量。
4. AI 不得虚构事实、推断敏感属性、人格诊断、颜值评价、成功率判断或暗示他人意愿。
5. 个人资料、照片、运营兴趣词库和 AI 文案上线前按风险等级审核；P0 不开放用户自定义兴趣。
6. 图片清理 EXIF/GPS；不采集或持续保存精确实时位置。
7. 页面使用 `noindex, nofollow`；媒体使用短期授权 URL，并具备 CSRF、防注入、CSP、限流和异常登录检测。
8. 用户能在“我的”中查看数据用途、修改权限、纠正/删除 AI 理解、关闭个性化以及申请注销或数据删除。
9. 权限变更和审核操作可审计；后台仅按最小权限展示，敏感值默认脱敏。
10. 未成年人准入漏失、隐藏字段泄漏或 AI 虚构任一发生，均阻塞发布。

## 13. 埋点与指标

### 13.1 核心事件

统一事件 `profile_onboarding_step`，通过 `action` 区分：

- `view`、`start`、`complete`、`back`、`skip_optional`
- `save_success`、`save_fail`、`resume`、`version_conflict`
- `validation_fail`、`exit_to_limited_browse`
- `submit`、`submit_success`、`submit_fail`

补充结果事件：`account_verification_result`、`adult_check_result`、`relationship_intent_save`、`interest_selection_save`、`sexual_orientation_save`、`photo_upload_result`、`personhood_verification_result`、`ai_summary_action`、`profile_review_result`、`permission_change`。

### 13.2 公共参数

`user_id_hash`、`session_id`、`request_id`、`draft_id_hash`、`onboarding_version`、`profile_version`、`step_id`、`step_index`、`entry_source`、`profile_status`、`action`、`duration_ms`、`network_type`、`error_code`、服务端时间。兴趣页可记录 0～5 的选择数量；性取向页只记录是否完成保存和公开开关是否开启，不记录具体值或选择数量。

禁止上报手机号、邮箱、验证码、完整生日、自我性别、性取向、候选偏好原值、兴趣具体 ID/文案、自由文本、照片 URL/内容、AI 摘要正文和字段权限明细。交往意向具体枚举也不进入通用步骤事件；专项分析若确需使用，必须单独经过隐私评审。普通埋点只允许上报是否完成、兴趣选项数量（0～5）、性取向是否开启公开及非敏感原因码；不得上报性取向选择数量。

### 13.3 核心指标

| 指标 | 建议口径 |
|---|---|
| 建档开始率 | 点击“开始建档”的新访客 / 看到欢迎页的新访客 |
| 账号验证成功率 | 至少一种验证成功账号 / 进入验证页用户 |
| 建档提交率 | 成功提交审核用户 / 账号验证成功用户，观察同会话与 24 小时两种窗口 |
| 有效完成时间 | 从开始第一个表单步骤到提交的前台有效填写时长，排除后台、审核等待和大于 30 秒的网络等待；目标 P50 为 3～5 分钟 |
| 步骤流失率 | 当前步骤 `view` 后未 `complete` 的用户占比 |
| 恢复完成率 | 触发 `resume` 后 24 小时内提交用户 / 恢复用户 |
| 审核通过率 | 首次审核通过用户 / 提交用户 |
| 保护指标 | 未成年人漏放 = 0；敏感埋点泄漏 = 0；隐藏字段泄漏 = 0；重复有效审核单 = 0 |

## 14. 非功能要求

- 4G 中档设备首屏 LCP P75 ≤ 2.5 秒、CLS ≤ 0.1、INP P75 ≤ 200ms。
- 自动保存 P95 建议 ≤ 800ms；超时不假装成功，用户可恢复。
- 支持现代浏览器最近两个大版本，重点覆盖 iOS Safari、Android Chrome、桌面 Chrome、Safari、Edge、Firefox。
- 核心流程达到 WCAG 2.1 AA：键盘可达、焦点清晰、语义化标签、错误可读、图片替代文本、非纯色提示。
- 支持 200% 缩放、系统字体放大和文案增长；320px 宽度下不横向滚动、不遮挡主操作。
- 尊重 `prefers-reduced-motion`；上传和 AI 处理提供文本进度与取消/重试。
- 服务端为资料、权限和审核状态的唯一真实来源；多端同步不得依赖浏览器本地存储。

## 附录 B：与当前前端原型的衔接

当前仓库默认注入的是已完成建档、已认证且 `RECOMMENDABLE` 的演示用户，尚无 onboarding 路由、草稿 DTO、状态守卫和审核补改页面。实现本需求时需要：

1. 为路由增加 onboarding 与状态页类型，而不是继续把未知路径落到推荐首页；
2. 新增允许字段缺失的草稿模型，不直接复用公开 `Person`；
3. 基于服务端准入结果控制首页、寻觅、消息、活动与写操作；
4. 让导航中的当前用户统一读取同一账号数据源，移除写死身份；
5. 将年龄、星座等可见性落实到个人卡和详情的公开 DTO，而不是只在“我的”页面显示开关；
6. 为首次用户补充合同、冒烟、响应式、移动遮挡、弱网、隐私和路由绕过测试。
7. 扩展现有 `RelationshipGoal` 三值枚举，新增性取向与独立公开开关，并将兴趣约束调整为 0～5 个；公开 `Person` 投影按权限省略敏感字段。
